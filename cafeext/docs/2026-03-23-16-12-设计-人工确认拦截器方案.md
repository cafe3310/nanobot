# 设计：人工确认拦截器 (Human-in-the-loop Tool Confirmation)

## 1. 任务背景 (Context)

随着 Agent 能力的增强（放开了 `exec` 权限并注入了多项金库技能），其工具执行的风险也随之升高。为了防止 AI 产生幻觉或执行误导性的破坏操作（如：错误的 `git push`、非预期的 `rm` 命令或覆盖核心文件），我们需要在工具实际运行前引入一层**人工确认**机制。

---

## 2. 核心机制 (Mechanism)

我们将利用 Sidecar 架构的 Monkey Patch 技术，对 `nanobot.agent.tools.registry.ToolRegistry.execute` 进行二次拦截。

### 2.1 执行流变化
1. **拦截点**: 当 `AgentLoop` 或 `Subagent` 调用任何工具时，请求首先进入我们的 `patched_execute`。
2. **视觉呈现**: 在终端打印出美化后的工具名称及其完整参数（JSON 格式）。
3. **阻塞等待**: 使用同步的 `input()` 函数暂停当前执行流，等待用户的选择。
4. **决策分支**:
    - **1 (批准)**: 恢复执行原始工具逻辑，并记录执行时长。
    - **2 (拒绝)**: 拦截执行，向 LLM 返回一个标准化的错误消息：`[Operation Cancelled] Reason: User denied execution.`。

---

## 3. 安全与交互设计

### 3.1 界面设计 (CLI View)
```text
==================================================
🛡️  [HUMAN-IN-THE-LOOP] Confirm Tool Execution
==================================================
🔧 Tool  : exec
📝 Params: {
  "command": "git push origin main"
}
--------------------------------------------------
👉 Action: [1] ✅ Execute | [2] ❌ Deny
Selection: _
```

### 3.2 错误反馈策略
当用户选择拒绝时，我们将该操作视为一种「受控的中断」。通过返回明确的「用户拒绝」信息，LLM 可以理解为什么任务没有继续，并可能尝试向用户询问原因或提供另一种方案，而不是陷入无限重试的逻辑。

---

## 4. 实施步骤 (Implementation)

1. **更新 `security.py`**: 在 `patched_execute` 中整合 `input()` 逻辑与审计日志记录。
2. **逻辑合并**: 确保审计日志（`tool_executing`）在确认**之前**触发，而 `tool_response` 在确认或执行**之后**触发。
3. **优雅降级**: 若处于非交互环境（虽在 CLI 下极少见），默认视为拒绝以确保安全。
