# 方案：nanobot 上游同步与升级计划

## 背景与动机
需要将核心的 `nanobot` 仓库同步升级至上游的最新版本（`https://github.com/HKUDS/nanobot.git`）。由于本项目采用了 Sidecar 架构（`cafeext/` 目录），并在运行时强依赖 Python 的 MonkeyPatch 机制来劫持和替换核心逻辑（例如强耦合了 `CustomProvider`、`AgentLoop` 和 `SubagentManager` 等），如果直接在当前分支合并上游代码，极易因为上游的重构（如函数签名更改、类重命名或模块移除）导致补丁失效，进而引发静默错误或导致应用无法启动。

## 范围与影响
- **上游更新**：涉及核心 Agent 循环、提示词上下文构建、工具注册表以及外部渠道连接器的代码更新。
- **自定义 Sidecar 逻辑**：`cafeext/py/wrapper/` 目录下的所有补丁脚本（如 `launcher.py`, `error_patch.py`, `subagent_patch.py`）极易受到上游代码变更的破坏。
- **测试验证**：在升级后，核心的单元测试用例必须能够和 Sidecar 附加包共同通过测试。

## 建议方案（安全分支合并策略）
我们采用“多阶段、隔离分支”的合并策略。所有的合并、冲突解决以及补丁修复工作都在一个独立的特性分支中进行。这样既能保证主干（`main`）的稳定性，又能为修复复杂的 MonkeyPatch 提供安全的调试环境。

## 实施步骤

### 阶段 1：准备与方案归档
1. **优先执行**：获取当前时间，将本升级计划完整写入开发日志，存放在 `cafeext/docs/YYYY-MM-DD-HH-mm-方案-nanobot上游升级计划.md` 中。
2. 确保当前工作区干净（无未提交的更改）。
3. 检查并添加上游远程仓库：`git remote add upstream https://github.com/HKUDS/nanobot.git`（若已存在则跳过）。
4. 拉取上游最新更改：`git fetch upstream`。
5. 创建隔离的升级分支：`git checkout -b chore/upgrade-upstream`。

### 阶段 2：合并与冲突解决
1. 将上游主分支合并到当前特性分支：`git merge upstream/main`。
2. 自动或手动解决由于两个仓库在共同文件上的修改而产生的显式 Git 冲突。
3. 仔细审查 `nanobot/` 目录下的核心变更，特别是寻找是否有被 Sidecar 劫持的类或方法被重命名、修改了参数列表或直接移除。

### 阶段 3：Patch 补丁修复与适配
1. 检查 `cafeext/py/wrapper/*.py` 脚本，处理任何可能的 `ImportError`。
2. 针对上游的新逻辑，更新补丁中的导入路径和伪造的引用（例如 `nanobot.agent.loop.AgentLoop`、`nanobot.providers.custom_provider.CustomProvider` 的初始化参数等）。
3. 如果上游引入了与 Sidecar 实现完全冲突的新特性，需权衡是禁用上游特性还是重写 Sidecar 补丁。

### 阶段 4：验证与测试
1. 确保 Python 环境加载了上游 `pyproject.toml` 中可能新增的依赖：执行 `pip install -e .`。
2. 运行 Sidecar 诊断工具 `nb doctor` 和 `nb --help`，验证启动序列能否成功加载所有补丁而不崩溃。
3. 运行完整的测试套件 `pytest tests/`，确认核心特性和集成依然稳定。
4. 在终端进行实际的人机对话测试，验证端到端功能：`nb agent --message "hello"`。

### 阶段 5：完成与提交
1. 确认所有测试通过后，将修复好的补丁和解决的冲突进行 `git commit`。
2. 撰写详尽的开发日志（符合 `doc-todo-log-loop` 规范），记录合并过程中发现的关键变更以及为了适配这些变更所做的 Patch 修改。
3. 将最终的 Diff 提交给用户审查，审查通过后再将 `chore/upgrade-upstream` 分支合并回 `main` 分支。

## 迁移与回滚策略
如果发现上游的变更属于颠覆性的架构重构，导致现有的 Sidecar MonkeyPatch 模式完全无法继续工作，我们将暂停合并操作，并评估是否需要将 Sidecar 逻辑原生移植到 `nanobot` 核心中。如有必要，我们可以直接放弃并删除 `chore/upgrade-upstream` 分支，安全地回到 `main` 分支的原始状态，不会对项目产生任何破坏。
