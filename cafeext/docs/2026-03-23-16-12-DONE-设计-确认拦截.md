# 设计：人工确认拦截器 (Human-in-the-loop Tool Confirmation)

## 1. 任务背景 (Context)

随着 Agent 能力的增强（开放了 `exec` 权限并配置了多项金库技能），工具执行的风险也随之升高。为了防止 AI 执行非预期的操作（如：错误的 `git push`、错误的 `rm` 命令或覆盖文件），需要在工具运行前引入人工确认机制。

---

## 2. 工作机制 (Mechanism)

利用 Sidecar 架构，对 `nanobot.agent.tools.registry.ToolRegistry.execute` 进行拦截。

### 2.1 执行流变化
1. **拦截点**: 当调用任何工具时，请求首先进入 `patched_execute`。
2. **信息展示**: 在终端显示工具名称及其完整参数（JSON 格式）。
3. **阻塞等待**: 使用 `input()` 函数暂停当前执行流，等待用户选择。
4. **决策分支**:
    - **1 (批准)**: 执行原始工具逻辑，并记录执行时长。
    - **2 (拒绝)**: 拦截执行，向 LLM 返回错误消息：`[Operation Cancelled] Reason: User denied execution.`。

---

## 3. 安全与交互设计

### 3.1 界面设计 (CLI View)
```text
==================================================
[HUMAN-IN-THE-LOOP] Confirm Tool Execution
==================================================
🔧 Tool  : exec
📝 Params: {
  "command": "git push origin main"
}
--------------------------------------------------
👉 Action: [1] Execute | [2] Deny
Selection: _
```

### 3.2 错误反馈策略
当用户选择拒绝时，该操作被视为受控中断。通过返回「用户拒绝」信息，LLM 可以理解任务未继续的原因，并尝试向用户询问或提供其他方案。

---

## 4. 开发步骤 (Implementation)

1. **更新 `security.py`**: 在 `patched_execute` 中整合 `input()` 逻辑与审计日志记录。
2. **逻辑合并**: 确保审计日志（`tool_executing`）在确认前触发，而 `tool_response` 在确认或执行后触发。
3. **降级处理**: 若处于非交互环境，默认视为拒绝以确保安全。
