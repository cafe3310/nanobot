# 调研：Peekaboo 与 picc 原生 UI 控制方案对比

## 1. 调研背景

为了扩展 nanobot 对操作系统（尤其是 macOS）原生界面的操作能力，我们调研了两个核心项目：`Peekaboo` 和 `picc`。它们代表了两种截然不同的技术路线。

---

## 2. 方案详解

### 2.1 Peekaboo (steipete/Peekaboo)
- **技术路线**: 基于 **Accessibility (辅助功能) API**。
- **核心原理**: 
    - 类似于浏览器的 DOM 树，Peekaboo 提取 macOS 窗口中的所有辅助功能元素。
    - 为每个元素分配唯一的标记（类似于 `agent-browser` 的 `@e1`）。
- **优势**:
    - **高稳定性**: 即使窗口移动或缩放，元素引用依然有效。
    - **结构化输出**: 提供 JSON 格式的元素树，Agent 能够理解按钮、文本框的语义。
- **劣势**: 
    - 部分应用（如自定义绘图软件、游戏）可能未适配 Accessibility API，导致某些元素不可见。

### 2.2 picc (andelf/picc)
- **技术路线**: 基于 **计算机视觉与坐标定位**。
- **核心原理**: 
    - 截取当前屏幕，利用视觉算法或简单的坐标逻辑进行元素识别。
    - 提供直接的鼠标/键盘模拟控制。
- **优势**:
    - **普适性强**: 理论上只要能显示在屏幕上的东西，picc 都能操作。
    - **轻量级**: 不依赖复杂的系统 API 授权（仅需录屏和控制权限）。
- **劣势**: 
    - **易失效**: 分辨率改变、窗口遮挡或布局微调可能导致操作失败。
    - **缺乏语义**: Agent 看到的只是一张图，需要额外的多模态模型解析才能确定点击位置。

---

## 3. 对比总结

- **Peekaboo** 类似于浏览器的 **Inspector**，适合操作办公软件、文件管理器等标准 UI 应用。
- **picc** 类似于人的 **双眼和手**，适合操作那些没有辅助功能接口的复杂界面。

---

## 4. 集成建议 (Roadmap)

我们建议采取「分层集成」策略：

1. **第一优先级**: 引入 `Peekaboo` 技能。
    - 利用其提供的结构化元素标记，完美复用我们现有的 `agent-browser` 式交互习惯。
2. **第二优先级**: 将 `picc` 作为 fallback。
    - 当 Peekaboo 无法识别目标窗口时，调用 picc 进行视觉定位。
